# Pending Conditional Fill Admission

Parent: `c285a998a4fead98c41bc4249417cc08e64623b7`.
This advances ordinary multi-GPU application admission. It is not executable or
launch authority, protected compiler-deployment qualification, or a GPU result.

## Implementation

`PendingWorkerV3ConditionalFillArtifactV1<K>::check` consumes the original recovered
publication and owned conditional refinement. It acquires one current-publication
token, reconstructs short-lived checked views of the retained compiler/analyzer
owners, and checks their exact association with the host request. It independently
reconstructs and compares the complete finalizer derivation.

Only then does it call the concrete inherited compiler-current-record auditor.
The client supplies its own fresh random challenge. The deterministic host request
identity is not a nonce. Publication currentness is rechecked immediately before
the service call and after it, including when the call fails. The successful audit
is consumed into exact subject/carriage evidence. All original owners and the
publication token remain retained by the pending artifact.

The constructor does not reacquire a nested publication lock, rerun Verus, reconstruct
an analyzer receipt, accept a generic affirmative provider, or convert conditional
proofs to unconditional evidence. Local association errors leave the service
endpoint available; a started service transaction consumes it on success or failure.
The pending owner is non-Clone and Send + Sync, with no unconditional executable
conversion. Failed construction consumes the supplied artifact and refinement.

## Qualification Scope

Worker bootstrap/replay/finalization, durable V2 publication/recovery, a fresh
authenticated analyzer execution and the actual protected owned-refinement producer.
The runtime lease and proof-construction auditor are dropped before pending admission.
The concrete FD195 client is admitted after proof production so its 30-second
deadline covers the service transaction rather than the expensive proof.

The compiler service is explicitly test-key-backed. It answers the actual client
request with canonical challenge-bound compiler and external-anchor signatures
for the exact carriage. This exercises the real client/import/host join, not
protected issuer deployment. No synthetic verifier or launch authorization is used.
The marker supplies checked test request identity, not generated argument ABI authority.

The six cases cover a retained positive, wrong marker, genuinely analyzed/proved
non-executable payload substitution, publication replacement during successful and
failed service calls, and service disconnection without replacement. Local rejections
must leave an open endpoint with no request. Every started transaction is followed
by a second audit requiring `AlreadyConsumed`. The positive compares original proof
and analyzer buffer addresses, proof binding and the service's fresh challenge;
retained currentness rejects replacement and accepts restoration. Verification,
protected compiler-origin, load and launch authority remain false.
