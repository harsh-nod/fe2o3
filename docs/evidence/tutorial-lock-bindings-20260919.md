# Tutorial input lock-binding repair

This is source-inventory maintenance, not execution, proof, hardware or
curriculum-maturity qualification.

At compiler base `7f355e4b748887495122fb0a06927b66613272d0`, all 49
`cargoLockSha256` bindings in the tutorial manifest were stale: 48 compiler
fixtures and one CPU-semantic-simulation source item referenced 13 lockfiles.
Their package-manifest and Rust-source-closure bindings still matched all
16 distinct packages. An ordinary locked Cargo metadata check does not
validate these separately retained tutorial digests.

The repair independently compared the old lockfile objects with current
files. The twelve standalone locks contain the source-observation crate's
added `rustix` edge. The root lock additionally contains the AMDGCN-model
`rustix` edge, simulator-differential/kernel-optimizer edge, and backend
AMDGCN-model/debugger edges. No external package version, source or checksum
changed. No lockfile was regenerated by this repair.

Only the 49 lock digests and their 49 dependent contract digests change in
`config/tutorial-kernel-manifest-v1.json`. The one curriculum golden changes
to `67f4296910a85ab0cbc49c73f6c260b5f3e8537db7263be4d022211bc78f2326`.
The source-item contract becomes
`108f9fae144da34a4ecef8e6b15307ee658aa3e58cc4efdb9d00acfde6c82de8`.
Source paths, package manifests, source closures, fixture rosters, policies,
qualification status and compiler/site publication pins are unchanged.

## Reproduction and observations

Use Python 3.11 or newer, required by the validator's `tomllib` import:

```sh
python3 -I -B scripts/validate-tutorial-kernel-manifest.py --require-curriculum
python3 -I -B scripts/validate-tutorial-kernel-manifest.py --emit-kernel-pairs
python3 -I -B scripts/validate-tutorial-kernel-manifest.py --emit-matrix gfx942
python3 -I -B scripts/validate-tutorial-kernel-manifest.py --emit-matrix gfx950
python3 -I -B scripts/tests/tutorial_kernel_manifest.py
python3 -I -B scripts/tests/tutorial_kernel_occurrences.py
python3 -I -B scripts/tests/tutorial_kernel_identities.py
bash scripts/tests/kernel-compile-matrix.sh
cargo metadata --locked --offline --format-version 1 > /dev/null
```

On mi350-2, the before-repair validator refused the actual stale fill-fixture
lock binding. After repair, required-curriculum validation, pair emission,
both target-matrix emissions and all 100 Python controls (64/12/24) pass.
The compile-matrix shell **test** also passes its stubbed-toolchain cases;
it does not compile or execute real GPU kernels.

That shell test now retains the actual Python interpreter that passed its
initial manifest checks when replacing PATH with its Cargo/ROCm stubs.
Otherwise its subprocesses silently reverted to the host's Python 3.10 and
failed to import `tomllib`. Its first matrix invocation now prints captured
failure output, matching the existing gfx950 failure behavior. The tests'
fake toolchains, compiler checks and negative cases are not weakened.

Validation used task-local CPython 3.12.14, not a global installation.
Before/after whole-checkout inputs were unchanged within each measured gate.
The final matrix/metadata input census (before this document) covered 5,839
files and 90,381,337 bytes, SHA-256
`17351e98222b70567105f8623d926bd8a4774b2562525c15a110cb9b587fbb41`.
The full locked offline dependency resolution passes. Its large JSON is
discarded rather than relaxing the task's one-MiB retained-output cap; the
initial capped-output attempt remains a failed setup run.

These results do not authenticate old execution receipts against new input
contracts. Source or lock changes introduced later require fresh input
binding checks and applicable qualification.
