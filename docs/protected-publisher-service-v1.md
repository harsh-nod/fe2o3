# Protected Publisher Reference Service V1

This document specifies the opt-in reference implementation in
`fe2o3-protected-publisher`. It is a conformance and deployment-design aid. It
is not deployed, is not production authority, does not create protected
evidence by itself, and does not change any parity row.

## Scope

The binary starts only with both `--serve` and `--config PATH`. Its listener
must be a loopback address. A production design therefore needs a separately
reviewed TLS frontend on the same host or private network namespace. The
frontend must preserve the request body and `Authorization` header byte for
byte, reject redirects, and never log either value.

The service accepts one operation, `POST /v1/receipts`. Admission is bounded
before the request body is read, and the slot remains held through durable
issuance. It verifies the bearer
as a GitHub Actions OIDC JWT, validates the canonical request generated by
`scripts/parity-publisher-client.py`, creates an Ed25519 publisher receipt in
the existing V2 TSV format, commits it to the replay database, and only then
returns the canonical response expected by that client.

There is no static bearer secret and no test mode in the production binary.
The RSA and Ed25519 material used by Rust tests is test-only and cannot pass a
production configuration or trust policy.

## Authentication Profile

The production configuration fixes:

- issuer `https://token.actions.githubusercontent.com`;
- JWKS URL `https://token.actions.githubusercontent.com/.well-known/jwks`;
- audience, repository name and numeric IDs;
- environment `protected-publisher`;
- merge-queue prefix for default branch `main`;
- caller and protected reusable-workflow paths; and
- a nonempty, bounded actor-ID allowlist.

Only RS256 JWTs are accepted. JWT header, claims, and JWKS JSON are parsed with
duplicate-member rejection. The selected JWKS entry must be the unique exact
`kid`, RSA signing use, and RS256 algorithm. When `x5t` is present in the JWT
header it must be a canonical 20-byte base64url thumbprint equal to the key's
JWKS thumbprint. Unknown algorithms, keys, members, or claim types fail closed.

The authority-bearing claim projection is required and typed. The service
reconstructs repository,
environment, subject, actor, event, ref, candidate SHA, caller workflow,
protected job workflow, run identity, issuer, audience, and runner environment
from protected configuration and request context. It compares the resulting
authorization object byte-semantically with the client's copy. Additional
bounded, duplicate-free provider metadata is tolerated but grants no authority;
documented `actor`, `ref_type`, and `repository_visibility` claims must be
strings when present. Names reserved by the local authorization object are
rejected. `exp`, `nbf`, and `iat` must be signed JSON integers, have a
five-minute skew allowance, and have a maximum ten-minute token
lifetime. Future `iat`, future `nbf`, stale `exp`, and inverted intervals are
rejected.

JWKS retrieval uses rustls certificate validation, HTTPS-only mode,
`ClientBuilder::no_proxy()`, and `reqwest::redirect::Policy::none()`. A
fresh-only bounded cache has one refresh leader and one outbound permit;
concurrent cold misses share the result. Cache expiry triggers a new fetch, and
stale keys are never used after expiry. Connect, headers, and every response
chunk share one absolute monotonic deadline. A redirect, non-200 response,
wrong final URL, wrong content type, invalid length, oversized body, timeout,
TLS failure, malformed JWKS, or outage fails closed.

## Bounds

The V1 implementation applies bounds before semantic allocation where
possible:

| Input | Bound |
| --- | ---: |
| HTTP request body | 65,536 bytes |
| bearer/JWT | 16,384 bytes |
| each encoded JWT segment | 12,288 bytes |
| JWKS body | 262,144 bytes |
| service response | 524,288 bytes |
| signed receipt | 262,144 bytes |
| HTTP headers | 32 headers / 32,768 aggregate bytes |
| JSON depth | 32 |
| JSON members | 512 |
| JSON lexical work | 4,096 tokens plus one pass over bounded bytes |
| individual JSON string encoding | 4,096 bytes |
| JWKS keys | 16 |
| private key file | 16,384 bytes |
| admitted HTTP requests | configured, 1 through 256 |
| request absolute deadline | configured, 1 through 30,000 milliseconds |
| JWKS fetch deadline | configured, at most request deadline and 10,000 milliseconds |
| JWKS fresh-cache lifetime | configured, 1 through 3,600 seconds |
| durable receipt identities | configured, 1 through 1,000,000 |
| SQLite main database | configured, 1 MiB through 64 GiB |
| SQLite busy wait | configured, 1 through 1,000 milliseconds |

All byte, depth, member, token, and storage counters use checked arithmetic.
The service does not return parser, crypto, database, key, token, or request
details in HTTP errors.

## Identities And Response

The request must be duplicate-free canonical JSON with sorted object keys, no
insignificant whitespace, and one trailing newline. V1 defines:

```text
request_sha256 = SHA256(canonical_request_bytes)
request_identity = SHA256("fe2o3-protected-publisher-request-identity-v1\0"
                          || canonical_request_bytes)
challenge = SHA256("fe2o3-protected-publisher-challenge-v1\0"
                   || lowercase_hex(request_identity))
evidence_identity = SHA256("fe2o3-protected-publisher-evidence-identity-v1\0"
                           || complete_signed_receipt_bytes)
```

The production `publisher_identity` and `signing_key_id` are `c` followed by
the first 63 hexadecimal characters of the canonical configuration SHA-256.
Any authority, path, bound, or key-slot configuration change therefore creates
a different identity that must be enrolled with the same public key before a
client will trust it. This preserves the existing receipt and client schema
while preventing a replaced configuration from silently using an already
enrolled identity.

The challenge is a signed receipt field, so the Ed25519 signature indirectly
binds the complete canonical request identity while retaining the existing
client-compatible receipt schema. The JSON response is exactly:

```json
{"challenge":"HEX","publisher_receipt_base64":"BASE64","request_sha256":"HEX","schema_version":1}
```

with sorted fields and a trailing newline.

## Replay Store

SQLite schema version 2 has unique constraints for `request_identity`, the
GitHub-signed `jti` replay identity, `request_sha256`, and
`evidence_identity`. The canonical request and committed response bytes are
stored together. Issuance uses `BEGIN IMMEDIATE`, WAL journaling,
`synchronous=FULL`, checked schema constraints, and a durable transaction.
The database parent is fsynced after creation.

Signing occurs inside the transaction. A signing or insert failure rolls back.
The response is returned only after commit. A concurrent duplicate waits,
then returns the exact stored bytes. Reusing a `jti` with different request
identity, digest, or body is a conflict. Database errors and uniqueness
surprises fail closed.

Retention never deletes an identity. After the configured retention period,
at most 64 expired rows per issuance have their request and response payloads
replaced by permanent identity tombstones. A tombstoned replay fails closed;
the same request cannot be reaccepted under either the old or a new `jti`.
Duplicates with retained payloads still return exact committed bytes. New
issuance stops at the configured row ceiling or SQLite main-database page
ceiling, while committed duplicates remain readable. The SQLite busy timeout
is capped at one second.

The database and key paths must be absolute; their directories must be real and
owner-only. The configuration and key final path components are opened with
`O_NOFOLLOW` and `O_CLOEXEC`, then owner, mode, regular-file type, link count,
and size are validated from the open descriptor. The service sets umask 0077
before opening runtime state and zeroizes the temporary PEM string after key
parsing. Private bytes are never formatted or logged.

## Configuration Schema

The configuration is canonical JSON schema version 1, owner-controlled, and
bounded to 65,536 bytes. Example placeholders are intentionally unusable:


## Dependency Rationale

The existing workspace had no HTTP/JWT/SQLite implementation. Versions are
exactly pinned in the crate manifest and transitively frozen in `Cargo.lock`:

| Dependency | Purpose |
| --- | --- |
| Axum 0.8.4 / Tokio 1.47.1 | small loopback HTTP service and absolute async deadlines |
| Reqwest 0.12.23 with rustls | validated HTTPS JWKS with redirects disabled |
| jsonwebtoken 10.3.0 with AWS-LC | RS256 primitive after independent bounded parsing and manual typed time validation |
| rusqlite 0.37.0, bundled SQLite | deterministic transactional replay store |
| ed25519-dalek 2.2.0 | existing receipt-compatible Ed25519 signatures |
| serde/serde_json | typed exact schemas after bounded duplicate-free parsing |
| sha2/base64/zeroize | versioned identities, wire encoding, PEM cleanup |

`bundled` SQLite avoids silently changing system SQLite behavior. Production
packaging must still inventory, scan, and reproduce the complete locked
dependency closure.

## Conformance

Run the opt-in harness with the intended Rust toolchain first in `PATH`:

```text
scripts/test-protected-publisher-service.sh
```

It runs debug and release tests, the deterministic hostile corpus, concurrent
duplicate and process-crash recovery tests, the existing Python client's
signature/trust-policy verifier, strict Clippy, formatting, and diff checks.
The mock issuer/JWKS and all signing keys are local deterministic fixtures.

## Production Deployment Checklist

Completion of this checklist requires separate operations and security review.
No item is established merely because the reference tests pass.

1. Build from a reviewed protected commit with `--locked`; archive the source,
   compiler, SBOM, vulnerability report, binary digest, and reproducibility
   result.
2. Provision an owner-only 0700 state directory on a local crash-consistent
   filesystem. Do not place SQLite WAL files on NFS or split replicas across
   independent databases.
3. Provision the Ed25519 private key out of band as a single-link 0600 file.
   Disable core dumps and debugger attachment; apply service sandboxing,
   memory, descriptor, process, and CPU limits.
4. Add the corresponding publisher public key and key ID to protected
   production trust before selecting it as active. Retain the previous public
   key until every old receipt has expired and every rollback window closes.
5. Install canonical production configuration as an owner-only, single-link
   0600 regular file. Compute and enroll its digest-derived service identity
   with the intended public key. Record a nonauthority enrollment run and
   compare every observed required GitHub claim with this profile.
6. Terminate TLS in a separately reviewed local frontend using a publicly or
   privately pinned trust chain. Expose only POST `/v1/receipts`; reject HTTP,
   redirects, alternate hosts, query strings, content encodings, and oversized
   headers/bodies. Never log Authorization or body bytes.
7. Restrict egress to GitHub's OIDC JWKS endpoint and required DNS. Remove
   proxy environment variables. Test certificate rejection, redirects,
   timeout, rotation, malformed JWKS, and outage behavior in staging.
8. Back up and restore the SQLite database with a transaction-consistent
   procedure. Exercise abrupt power-loss, full disk, read-only filesystem,
   corrupt WAL, lock contention, and restore-before-retry scenarios.
9. Put `protected-publisher` behind required reviewers and deployment branch
   policy. Install and independently verify the no-bypass repository rules,
   protected workflows, merge queue, and exact required check identity.
10. Rate-limit by authenticated workflow identity at the frontend while
    preserving duplicate retries. Alert only on bounded public error codes and
    aggregate counts; do not export token, request, receipt, or key material.
11. Run client-service conformance with production public trust but a
    nonauthoritative destination. Independently verify response signatures,
    concurrent idempotency, replay conflicts, key rotation, and crash recovery.
12. Obtain an independent security review of code, deployment manifests,
    network policy, key custody, database recovery, GitHub settings, and actual
    enrolled claims.

The reference remains single-node and loopback-only. Its SQLite page ceiling
does not account for short-lived WAL and filesystem metadata overhead. It does
not provide an inbound TLS frontend, raw HTTP request-smuggling defense at that
frontend, distributed rate limiting, HSM-backed signing, supervision, backup,
restore, corruption repair, monitoring, or tested physical power-loss
recovery. Tests use a synthetic issuer profile rather than an enrolled live
GitHub token. These are deployment blockers, not properties established by
this crate.

Only after those external controls and separately reviewed hardware/proof
evidence exist may a protected promotion be evaluated. This reference layer
alone must leave the parity dashboard unchanged.
